# 关于 mHBS 的 SLH-DSA 架构表述：事实、证据与建议措辞

“宏操作级微程序架构”：本设计采用宏操作级微程序架构：program、template 和 descriptor 控制 SLH-DSA 的操作顺序、参数与数据路由，专用 RTL 状态机执行链迭代、树归约及双 Hash lane 调度。

“对slhdsa分析发现，该hash based算法本质上是在对hash的“preimage”（hash的输入数据）进行变化，在抽象层面形成tree、chain等结构。那么本项目在深入分析了slh-dsa的hash输入数据整合方式进行抽象，提出多种宏以及模板，让整个设计能高效使用hash加速器，最终实现完整算法，且有较高atp，且留有未来进一步扩展的可能性”

## 1. 结论

原表述抓住了本项目的主要架构思路：把 SLH-DSA 中重复出现的哈希调用，连同其输入构造、链迭代、树归约和结果路由，组织为可由镜像驱动的专用宏操作，再复用 Keccak/SHAKE 计算硬件。它需要三处修正：

1. **“变化 preimage”不足以概括算法。** 更准确的是“按规范构造不同的哈希输入字节串，并把哈希输出按链和树的依赖关系继续使用”。密码学中的 *preimage／原像* 往往指针对一个给定摘要求得的输入，在这里用“哈希输入”更清楚。
2. **“提出多种宏以及模板”要说明层级。** 项目实现的是五类宏操作和独立的 program、template、descriptor 镜像；模板只承载单条宏命令，配方、树参数和路由主要在 descriptor 中。宏和模板解决的是**控制与数据组织**，不是替换底层 Keccak 算法。
3. **“较高 ATP”方向相反。** ATP = 等效面积 × 签名时间，**越低越好**。当前 v4.2 布局修订 3 已完成功能验证及 post-synth 测量，尚无其自身的 post-route 频率，因此应写“以降低签名 ATP 为目标”或“具有已测的归一化 ATP”，不应直接声称其最终 ATP 较低。

## 2. 逐句判断

| 原表述 | 判断 | 更精确的含义 |
|---|---|---|
| “SLH-DSA 是 hash-based 算法” | 正确 | FIPS 205 定义了基于哈希/XOF 的六类函数，以及 WOTS+、FORS 和 hypertree 的组合。 |
| “本质上是在对 hash 的 preimage 进行变化” | 有启发性，但过于简化 | 各次调用改变密钥/种子、地址、域、消息或节点列表等输入，并有**输出到下一次输入**的依赖；还必须完成摘要解析、路径选择、认证节点输出和签名组装。 |
| “在抽象层面形成 tree、chain 等结构” | 基本正确 | 链是逐步依赖的函数复合；树是带地址和节点编号的二叉归约。它们既是哈希调用图，也是签名方案规定的数据结构。 |
| “分析 hash 输入数据整合方式进行抽象” | 正确，可写得更具体 | 项目区分输入配方、吸收/填充、链与树调度、暂存及结果路由，使短输入与长输入分别走合适的数据路径。 |
| “提出多种宏以及模板” | 与实现一致 | 具体为五类宏操作、三层独立微码镜像和 descriptor 配方；不能据此声称宏指令思想本身为首次提出。 |
| “让整个设计高效使用 hash 加速器” | 有实现依据，效率需用指标限定 | 当前核复用两个 U2 Keccak Hash lane，宏内部批量发起哈希；“高效”应落到 LUT/FF、周期、频率和 ATP 的可复现实测上。 |
| “最终实现完整算法” | 需限定范围 | 当前生产 RTL 实现 SLH-DSA-SHAKE 的 128f/192f/256f **内部 Keygen 与 Sign 流程**；种子、随机量和 Sign 公钥根由外部提供。不包含 Verify、随机数生成、SHA-2 参数集、s 参数集或独立的安全认证。 |
| “且有较高 ATP” | 用词错误，且当前阶段证据不足 | ATP 低才好。布局修订 3 的 100 MHz ATP 是归一化估算；最终值须使用该版本的布线面积和通过时序的频率。 |
| “留有未来进一步扩展的可能性” | 可以作为架构潜力 | 扩展新配方、参数集或算法通常还需修改 RTL、软件模型和验证；不能保证仅换镜像即可支持。 |

算法事实依据为 [NIST FIPS 205，第 4、5、9、11 章](https://nvlpubs.nist.gov/nistpubs/fips/nist.fips.205.pdf)；项目实现依据为 [当前 ABI](../ABI.md)、[生产软件编译器](../../model/unified_hbs.py) 和 [当前顶层](../../rtl/top/mhbs_top.sv)。

## 3. “哈希输入变化”到底解释了什么

FIPS 205 的 SHAKE 实例使用 `PRF_msg`、`H_msg`、`PRF`、`F`、`H`、`T_ℓ` 六类函数，它们都调用 SHAKE256，但**拼接的输入和截取的输出不同**。例如：

```text
PRF_msg : SK.prf  || opt_rand || M            → n 字节随机化值 R
H_msg   : R       || PK.seed  || PK.root || M → m 字节消息摘要
PRF     : PK.seed || ADRS     || SK.seed      → n 字节秘密元素
F       : PK.seed || ADRS     || 一个 n 字节节点 → n 字节
H       : PK.seed || ADRS     || 两个 n 字节节点 → n 字节
T_ℓ     : PK.seed || ADRS     || ℓ 个 n 字节节点 → n 字节
```

这里的 `ADRS` 是包含类型、层、树、叶、链步或节点位置的结构化地址；它不是可任意变化的标签。改变地址、拼接顺序、域或输出长度会改变协议计算结果。FIPS 205 的 [函数与地址定义](https://nvlpubs.nist.gov/nistpubs/fips/nist.fips.205.pdf)及 [SHAKE 实例化公式](https://nvlpubs.nist.gov/nistpubs/fips/nist.fips.205.pdf)给出了精确规范。

“输入变化”只覆盖了**单次调用**。算法层还有以下必须执行的依赖：

- **WOTS+ 链：**上一步输出成为下一步输入，步号写入地址；消息及校验和数字决定应输出链上的哪一个值。全链末端经 `T_ℓ` 得到公钥。FIPS 205 的 `lg_w=4`，因此 128f/192f/256f 分别有 35/51/67 条链，每条最多 15 步。
- **FORS：**由消息摘要选出各树的目标叶，生成其秘密值及认证路径；多个 FORS 根再压缩成一个公钥。叶的秘密值、节点哈希、根列表哈希共享底层 SHAKE，但地址和输入来源不同。
- **Hypertree：**WOTS+ 生成叶相关值，Merkle 树归约生成根；签名还要输出目标路径上的兄弟节点，并逐层更新树号和叶号。后续层要签的是前一层的根。
- **消息控制：**`H_msg` 的结果还用于选择 FORS 数据及 hypertree 起点，属于摘要解析和控制决策，而非另一次“变化输入”就能描述完的工作。

所以本项目可用下式概括，但它是**硬件设计视角**，不是对 SLH-DSA 数学定义的替代：

```text
完整算法 = 输入构造/域与地址 + SHAKE 调用 + 链/树依赖调度
         + 中间值存储与路由 + 消息选择 + 签名输出
```

## 4. 项目实际如何抽象

当前生产格式是 `slh64_v4.2` 布局修订 3，保留 ABI 4 宏语义。三份独立镜像分别是 **32×64 位 program、16×64 位 template、32×64 位 descriptor**。Job 从顶层参数进入，消息从 64 位握手端口进入；Keygen/Sign 由同组镜像的两个入口分别启动。详情以 [当前 ABI](../ABI.md) 和 [v4.2 接口文档](External_Job_Message_Interface.md)为准。

| 层次 | 本项目承担的工作 | 与原表述的关系 |
|---|---|---|
| program | SINGLE/RUN/LOOP/HALT、宏操作顺序、坐标和重复次数 | 决定“什么时候、对哪个叶/层”做计算 |
| template | 一条宏的类别、descriptor 引用、路由引用和 CAPTURE/AUTH 等标志 | 把重复的算法步骤压缩为宏命令 |
| descriptor | Hash shape、域、输入数、链数、树高、地址引用和结果路由 | 描述“当前哈希调用的输入如何构造，输出去哪” |
| `mhbs_hbs` | 展开链/树循环、调度两个 Hash lane、管理节点及结果 | 执行超出单次 Hash 的依赖结构 |
| Hash lane / Keccak | 按配方准备短/长输入、SHAKE 吸收/填充、U2 置换和链反馈 | 共享高成本的数据通路 |

具体映射不是“一种标准函数对应一种宏”。`PRF_msg`/`H_msg` 主要由 `MESSAGE_PRF`/`MESSAGE_DIGEST` 配方加 `HASH` 宏执行；`PRF`、`F`、`H` 使用地址型配方，并在 `CHAIN` 或 `TREE` 宏内重复调用；`T_ℓ` 则在 WOTS+ 端点列表或 FORS 根列表归约时由 `ADDRESS_LIST` 配方执行。也就是说，**宏控制调用关系，配方控制哈希输入**。源码对应 [镜像生成](../../model/unified_hbs.py)、[序列器](../../rtl/sequencer/mhbs_program_sequencer.sv)、[宏执行器](../../rtl/top/mhbs_hbs.sv)和 [Hash 输入配方 lane](../../rtl/hash_lane/mhbs_recipe_lane.sv)。

这层抽象可以减少逐次 Hash 发指令的开销，允许链内反馈和宏内双 lane 并行，并复用相同的 Keccak 置换单元。它**不自动**保证最小面积或最短周期：配方选择器、宽状态、端点/根存储以及控制寄存器也占资源；最终效果必须靠候选综合和布线结果判断。

## 5. “高效”和 ATP：当前能证明到哪里

当前 v4.2 **外部 Job/消息、布局修订 3** 候选 `sync_c0` 已通过六组 Keygen/Sign 输出和计数验证、共同核结构检查及 post-synth 测量；其自身**尚无 post-route 频率**。下表使用完整顶层面积 **7,166.375 等效 Slice** 和 **假定 100 MHz**，仅用于同频归一化，不是布线验收值。数据来自 [原始结果](../../manifests/experiments/unified_hbs_v4.2/external_job_message/candidates/sync_c0/result.json)和 [接口测量报告](External_Job_Message_Interface.md)。

| Profile | Sign 周期 | 等效面积 | Sign 时间 @100 MHz | Sign ATP @100 MHz |
|---|---:|---:|---:|---:|
| SLH-DSA-128f | 731,050 | 7,166.375 Slice | 7.31050 ms | 52,389.784 Slice·ms |
| SLH-DSA-192f | 1,252,461 | 7,166.375 Slice | 12.52461 ms | 89,756.052 Slice·ms |
| SLH-DSA-256f | 2,583,908 | 7,166.375 Slice | 25.83908 ms | 185,172.537 Slice·ms |

面积公式为 `LUT/4 + FF/8 + BRAM36×232.4 + DSP×102.4`；本候选是 **23,219 LUT、10,893 FF、1,456 LUTRAM、0 BRAM、0 DSP**。LUTRAM 已计入 LUT，不再重复相加。签名 ATP 的通式为：

```text
ATP [Slice·ms] = 等效面积 [Slice] × Sign 周期 / (实测频率 [MHz] × 1000)
```

历史布局修订 2 的另一候选曾完成 post-route，面积 **7,249 Slice**、频率 **101.010101 MHz**、三个 Sign ATP 为 **52,463.876 / 89,882.989 / 185,434.416 Slice·ms**；该频率**不能移用**到现在的布局修订 3。历史布线结果见 [v4.2 优化报告](Optimization_and_Paper_Comparison.md)。

因此可以写“当前实现经过功能验证，已给出综合面积和周期，具备可量化的 ATP 优化基础”；不能写“当前版本已经实现较低的最终 ATP”，更不能写“较高 ATP”作为优点。如果要对外声称“优于某架构”，应同时注明相同或不同的参数集、硬件资源口径、实测频率、消息长度与比较阶段。

## 6. “可扩展”的边界

架构留有扩展空间的依据是：宏与配方分层、同一套源代码支持三种 `n` 和树参数、program 可以改变执行顺序和循环；Keygen 与 Sign 也共用同一核。但**镜像只能组合 RTL 已实现的能力**。当前生产核仅支持 SLH-DSA-SHAKE 的三个 f 参数点，Hash shape、链数、节点存储、消息最长 87 字节及输出协议都有界。增加 SLH 的 SHA-2/s 参数集、Verify，或重新加入 XMSS/LMS，可能需要新增配方、数据通路、存储和验证；“只换镜像即可扩展算法”不是已验证结论。

此外，当前测试证明的是指定输入和覆盖范围内的功能与周期一致性；它本身不证明新参数集的正确性、形式化安全性或抗侧信道能力。将“扩展性”表述为**架构上的扩展路径**，比表述为“已支持任意哈希签名算法”准确。

## 7. 推荐替换表述

> 对 SLH-DSA-SHAKE 的分析表明，签名与密钥生成包含大量具有固定输入构造规则的 SHAKE 调用，其输出通过 WOTS+ 链、FORS 树和 hypertree 形成连续依赖。本项目将输入配方、宏操作顺序、链与树的迭代以及结果路由分层抽象为 program、template、descriptor 和五类专用宏操作，由共同的 Keccak 计算硬件执行。当前实现覆盖 SLH-DSA-SHAKE-128f、192f、256f 的 Keygen 与 Sign，已通过软件模型和 RTL 功能验证，并取得可复现的综合面积与周期结果。该结构为继续优化签名面积时间乘积（ATP）及扩展已定义的计算能力提供了基础；当前接口版本的最终 ATP 仍须以其自身 post-route 频率确认。

若用于论文摘要，建议把“提出”具体化为本项目与先前架构的**可核验差异**，并在完成同口径布线比较后给出性能百分比。仅凭“使用宏/模板驱动 Hash”不足以构成独立的新颖性或性能结论。
