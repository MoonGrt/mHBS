# mHBS 与 SLOTH 存储结构分析及贡献验证方案

日期：2026-10-02。本文整理本项目 Git 历史、已有综合证据及本地 `source/sloth` 源码分析；未启动新的综合、布线或性能测试。

## 1. 核心结论

mHBS 最早的完整微码实现使用 BRAM，后来通过签名流式输出、紧凑控制、数据生命周期复用及 Hash 数据通路优化，实现了 **0 BRAM、1,112 LUTRAM** 的共同核。其控制镜像逻辑容量为 **512 B**。

这可以形成“面向数据生命周期的低存储微码架构”贡献：微码减少控制表示空间，专用数据通路减少中间数据搬运、重复暂存和签名缓冲需求。相对 RISC-V＋Hash 的具体存储缩减比例，仍需要精简固件、实际栈峰值和一致接口条件下的对照实验。

SLOTH 已采用小工作集树遍历和链内加速，因此不能将“无需整树缓存”或“链内反馈”直接当作相对 SLOTH 独有的创新。值得重点验证的是控制存储、跨阶段存储共享，以及避免在签名过程中回读完整结果缓冲的设计。

## 2. 术语与计量边界

| 项目 | 本文定义 | 注意事项 |
|---|---|---|
| 控制存储 | 程序、模板、描述符及执行所需只读常量 | 软件代码与微码应采用相同功能范围 |
| 数据工作集 | 同时存活的中间节点、上下文、树栈和暂存 | 与源码数组容量之和不同 |
| 结果缓冲 | 保存完整或部分签名、密钥结果的空间 | 若放到外部，应明确外部存储及接口条件 |
| B / KiB | 字节 / 1,024 字节 | 不与 LUTRAM 数量混用 |
| LUTRAM | 实现分布式存储的 LUT 资源数量 | 1,112 LUTRAM 不等于 1,112 B，也不等于 1 KiB |
| BRAM36 等效数量 | RAMB36 数量加 RAMB18 数量的一半 | 与逻辑有效字节数不同 |
| FF | 触发器资源 | Hash 状态、暂存和控制均可能占用 FF |

**0 BRAM 不等于没有存储。**完整硬件成本还包括分布式 RAM、镜像 ROM、寄存器状态及选择逻辑。LUTRAM 已包含在总 LUT 中，不能重复相加。

## 3. mHBS 存储演进

### 3.1 历史阶段

| 阶段 | 存储资源或容量 | 关键变化 | 证据 |
|---|---|---|---|
| 最早微码控制切片 | 1 RAMB36；程序 512×64 bit＝4 KiB | 同步程序存储，FETCH→RUN | H1 |
| 早期完整 SLH-DSA 微码实现 | 7 RAMB36 | 通用 Scratchpad、数据构造与搬运；128f Sign 约 1,517 万周期 | H2 |
| 初始双 lane 水平架构 | 13 RAMB18＝6.5 RAMB36 | 节点使用小型 LUTRAM；17,088 B 完整签名保存在片内，签名 RAM 占 12 RAMB18 | H3 |
| 直接签名输出 | 1 RAMB18 | 删除完整 Signature RAM，计算过程中输出结果 | H4 |
| 紧凑控制和数据通路组合优化 | 0 BRAM | 紧凑 descriptor、状态复用、控制裁剪及关闭统计等优化后消除剩余 BRAM | H4 |
| v4.1 统一架构 | 0 BRAM；2,312→2,248 LUTRAM | template 物理宽度由 128 位降为 64 位 | H5 |
| SLH 专用化与 v4.2 紧凑布局 | 0 BRAM；1,904→1,456 LUTRAM | 缩小镜像和支持范围，精简通用存储结构 | H6 |
| FORS/WOTS 共享列表存储 | 0 BRAM；1,454→1,112 LUTRAM | 两类数据生命周期不重叠，删除独立 FORS 根存储 | H7 |
| 六参数共同核及后续逻辑优化 | 0 BRAM；1,112 LUTRAM | 支持六种 f/s 参数，主要节点数组容量保持不变 | 当前架构及候选报告 |

1,456 与 1,454 来自不同历史版本。共享列表这一项的直接前后对照为 **1,454→1,112，减少 342 LUTRAM，约 23.5%**；不能将二者混写。

这些阶段包含不同算法范围、接口、器件速度等级及综合边界。历史曲线用于解释设计演进，不能直接代替同条件消融。尤其早期控制切片不是完整密码核。

### 3.2 控制程序压缩的独立证据

历史水平控制核心还比较过未压缩与压缩控制存储：未压缩的 6,144×128 bit 控制 ROM 使用 32 RAMB36；压缩 token 实现使用 1 RAMB36，模板表另占 104 LUTRAM。这一局部实验支持重复任务压缩的收益，但不是完整签名核“32→1 BRAM”的测量，不能混入上述整核曲线。见 H3。

当前控制镜像如下：

| 镜像 | 逻辑布局 | 容量 |
|---|---|---:|
| Program | 16×64 bit | 128 B |
| Template | 16×64 bit | 128 B |
| Descriptor | 32×64 bit，双读接口 | 256 B |
| 合计 | 单个参数集装载的一组镜像 | **512 B** |

RUN、LOOP 和宏操作展开重复计算，避免保存逐个 Hash 任务。六参数通过替换镜像配置，不在核内同时保存六份镜像。Template 继续由文件加载，没有固定为 RTL 常量。512 B 是逻辑容量；双读映射等物理开销需以外壳报告核算。

### 3.3 数据存储缩减机制

1. **流式签名输出**：删除完整签名缓冲，将存储需求与完整签名长度解耦。接收端必须满足输出吞吐要求，外部缓冲应按系统边界另计。
2. **FORS/WOTS 存储共享**：FORS 根列表压缩完成后，WOTS 端点覆盖同一存储区域；避免两份不同阶段使用的列表同时分配。
3. **有限树工作集**：保留计算所需树栈和认证路径，不保留完整树。
4. **Hash 局部反馈和暂存复用**：链值在 lane 内继续计算，减少写回和重复副本；收益可能体现为 FF 或逻辑 LUT 下降，不一定改变 LUTRAM。

### 3.4 主要节点数组与综合边界

| 节点数组 | 逻辑容量 |
|---|---:|
| FORS/WOTS 共享列表：68×256 bit | 2,176 B |
| 树栈：16×256 bit | 512 B |
| 认证路径：16×256 bit | 512 B |
| 合计 | **3,200 B** |

上述合计不含密钥、消息、摘要、Hash 状态和其他暂存寄存器，不能称为整个设计的总存储位数。

前述讨论引用的固定写银行候选 `lut21k_20261002_v1_bank`，共同核综合为 **21,044 LUT、8,323 FF、1,112 LUTRAM、0 BRAM、0 DSP**。其共享列表实例占 684 LUTRAM，HBS 核本层占其余 428 LUTRAM；三组外壳镜像 ROM 不在该共同核面积内。

整理报告时，当前核指针已指向 `lut21k_20261002_v1_route_alias`，对应结果记录 **21,043 LUT、7,932 FF、1,112 LUTRAM、0 BRAM、0 DSP**，阶段为 `post_synth_core_only`，频率为空。两份数据绑定不同候选，不能混用面积、周期或频率；本文存储结论不依赖这两者之间的逻辑面积差异。当前指针可能随后续工作继续更新。

参考：[架构说明](../Architecture.md)、[route_alias 分层报告](../../manifests/experiments/unified_hbs_v4.2/external_job_message/candidates/lut21k_20261002_v1_route_alias/synthesis/core_hierarchical.rpt)、[route_alias 候选结果](../../manifests/experiments/unified_hbs_v4.2/external_job_message/candidates/lut21k_20261002_v1_route_alias/result.json)。

## 4. SLOTH 存储结构

本节针对本地 `source/sloth` 的默认未掩码 SHAKE 实现。默认配置还启用 SHA2，当前通用固件并非 SHAKE-only 最小固件。

```text
RISC-V CPU
 ├─ 取指端口 ─────────┐
 ├─ 数据读写端口 ─────┴─ 128 KiB 主 RAM
 │                       ├─ 程序及只读常量
 │                       ├─ 全局数据、堆
 │                       └─ 栈：上下文、中间变量、消息、密钥、签名缓冲
 └─ MMIO ────────────── Keccak 加速器
                         ├─ 200 B 状态
                         ├─ 32 B ADRS
                         ├─ 32 B PK.seed
                         └─ 32 B SK.seed
```

### 4.1 主 RAM：程序与数据共享

`RAM_XADR=17` 配置 128 KiB 主 RAM，起始地址为零。`fpga_ram` 是同一份 32 位数组：一端口读写数据，另一端口只读取指；初始栈指针设为 `RAM_SIZE-4`。程序和数据并非各占 128 KiB。

128 KiB 是配置容量，不是某个 SLH-DSA 参数集的实际峰值需求，也不是最低可运行容量。具体 FPGA BRAM 数量需要综合报告，不能直接由容量当作实测结果。

依据：[配置](../../source/sloth/config.h)、[RAM RTL](../../source/sloth/rtl/fpga_ram.v)、[CPU 连接](../../source/sloth/rtl/sloth_top.v)、[链接脚本](../../source/sloth/flow/riscv.ld)。

### 4.2 程序和静态数据

对本地 `source/sloth/firmware.elf` 执行 `size -A` 得到：

| 段或类别 | 大小 | 说明 |
|---|---:|---|
| `.text` | 32,404 B | 指令代码 |
| `.rodata` | 4,412 B | 只读常量 |
| `.data + .sdata` | 1,416 B | 已初始化可写数据 |
| `.bss + .sbss` | 1,704 B | 零初始化数据 |

表中未计入栈、动态堆及少量初始化段和对齐间隙。ELF 的调试信息不应计作片上运行存储。

该固件包含 SHAKE、SHA2、KAT、驱动及 C 运行库。32,404 B 不能直接解释为 SHAKE 签名必需代码量，不能据此宣称相对 512 B 微码的算法控制存储缩减比例。

### 4.3 中间数据：软件栈和上下文

| 中间数据 | 源码声明容量 | 用途 |
|---|---:|---|
| WOTS 端点数组 `tmp` | 67×32＝2,144 B | 生成或恢复 WOTS 公钥前的端点列表 |
| XMSS 树栈 `h` | 9×32＝288 B | 非递归子树归约 |
| FORS 树栈 `h` | 14×32＝448 B | 非递归 FORS 子树归约 |
| FORS 根数组 `root` | 35×32＝1,120 B | 汇集 FORS 根并压缩 |
| WOTS 链长 `vm` | 67×4＝268 B | 链迭代长度 |
| FORS 索引 `vi` | 35×4＝140 B | 摘要解析得到的叶索引 |
| 消息摘要 `digest` | 49 B | H_msg 输出 |
| 算法上下文及 Hash 上下文 | 另计 | 密钥副本、参数指针、地址及 Hash 状态 |

SLOTH 已使用小工作集树遍历，无需保存整棵 FORS/XMSS 树。表中数组按支持参数的最大值声明；例如 128f 的 WOTS 端点有效数据只有 35×16＝560 B，但通用代码声明的 `tmp` 是 2,144 B。

**不能将以上所有数组相加得到峰值 RAM。**不同调用阶段会复用栈空间；同时还应计入嵌套调用、寄存器保存和对齐。实际需求应通过目标固件栈水位及调用路径测量。

依据：[上下文与容量常量](../../source/sloth/slh/slh_ctx.h)、[算法工作数组](../../source/sloth/slh/slh_dsa.c)、[SHAKE 软件上下文](../../source/sloth/slh/sha3_api.h)。

### 4.4 签名缓冲及其回读用途

`slh_sign(sig, …)` 将完整签名写入调用者提供的连续地址空间。由本地参数和 `slh_sig_sz()` 公式得到：

| 参数集 | 完整签名长度 |
|---|---:|
| SHAKE-128f | 17,088 B |
| SHAKE-192f | 35,664 B |
| SHAKE-256f | 49,856 B |
| SHAKE-128s | 7,856 B |
| SHAKE-192s | 16,224 B |
| SHAKE-256s | 29,792 B |

本地测试框架声明 `sm[MAX_SIGN + 33 * KATNUM]`。`MAX_SIGN=50000`，默认 `KATNUM=10` 时容量为 50,330 B，用于签名和追加消息。这是通用测试分配量，不是每个参数集的最小签名空间；具体构建若覆盖 KATNUM，容量随之变化。

签名内存还承担中间输入功能：

- `slh_do_sign()` 调用 `fors_sign()` 后，通过 `fors_pk_from_sig()` 回读 FORS 签名恢复公钥。
- `ht_sign()` 生成某层 XMSS 签名后，通过 `xmss_pk_from_sig()` 回读该层签名恢复下一层需要的根。

因此，将当前实现改为只写不回读的流式输出，需要调整根计算或保留策略。源码并不证明软件在算法上必须保存完整签名；经过调度修改、分块保留或重计算，可以探索更低 RAM 实现。

测试框架的 `[STK]` 在算法调用前填充、返回后探测调用者栈指针以下的空间，**不包含调用者已经分配的 `sm` 大缓冲区**。算法栈峰值和调用者缓冲必须分项记录，避免漏算或重复计算。

依据：[测试框架](../../source/sloth/drv/test_bench.c)、[栈探测](../../source/sloth/drv/test_stack.S)、[签名流程](../../source/sloth/slh/slh_dsa.c)、[参数定义](../../source/sloth/drv/sloth_shake.c)。

### 4.5 加速器内部状态

未掩码 Keccak 加速器声明 `mem[0:73]`，每项 32 位，共 296 B：200 B Keccak 状态、32 B ADRS、32 B PK.seed、32 B SK.seed。轮计数、链控制及总线寄存器另计。这些字段通过 MMIO 映射；宽并行状态更新的物理映射应以综合网表为准，不能把 RTL 中名为 `mem` 的数组直接记作 BRAM。

SLOTH 已支持专用填充和 WOTS 链内迭代。普通流式 SHAKE 路径另外保留软件状态，`keccak_f1600()` 将 50 个 32 位状态字传入加速器，再读回软件缓冲。因此需要区分专用链路径与普通流式 Hash 路径的存储和传输开销。

依据：[Keccak 寄存器与数据通路](../../source/sloth/rtl/keccak_sloth.v)、[SHAKE 驱动](../../source/sloth/drv/sloth_shake.c)。

## 5. 两种架构的对照与贡献定位

| 比较项 | 本地 SLOTH | mHBS | 可验证的差异 |
|---|---|---|---|
| 控制表示 | RISC-V 代码、常量及运行库 | Program＋Template＋Descriptor | 相同功能范围下的代码/镜像容量 |
| 中间工作集 | 软件栈、上下文、树栈和列表 | 专用数组、寄存器及阶段共享 | 实际峰值与物理资源 |
| 签名结果 | 连续缓冲，签名过程中还会回读 | 计算过程中按节点输出 | 完整结果缓冲、分块缓冲及回读流量 |
| 树存储 | 小栈，无需整树缓存 | 树栈及认证路径 | 不能将无整树缓存作为独有优势 |
| Hash 链 | 已有硬件链迭代 | lane 内部反馈 | 增量收益需同功能消融 |
| Host/Hash 交互 | CPU MMIO 调度和搬运 | 微码触发专用数据通路 | 事务次数、传输字节及等待周期 |

### 5.1 建议贡献表述

> 提出一种面向 SLH-DSA 的低存储微码架构，通过流式签名生成、跨阶段存储共享及 Hash 局部反馈缩减片上工作集。在支持六种 SHAKE 参数集及 Keygen、Sign、Verify 的条件下，共同核无需 BRAM，仅使用 1,112 个分布式存储 LUT，控制镜像逻辑容量为 512 B。

1,112 LUTRAM 属于共同核口径，512 B 镜像位于外壳；寄存器状态仍需计入完整设计成本。与 SLOTH 的优势幅度和新增机制的独立收益尚待以下实验验证。现有证据支持“低片上存储”，不支持“存储接近零”“全局最低存储”或“所有软件实现必须缓存完整签名”。

### 5.2 已有证据与缺口

| 结论 | 证据状态 |
|---|---|
| 早期完整微码核确实使用 BRAM，后续降至零 | 历史报告支持；不同阶段不构成统一消融 |
| FORS/WOTS 共享存储减少 LUTRAM | 直接前后对照：减少 342 LUTRAM，约 23.5%；正常输出和周期保持一致 |
| 六参数控制镜像逻辑容量为 512 B | 当前布局和源码支持 |
| SLOTH 默认主 RAM 为 128 KiB | 配置和 RTL 支持；不是实际峰值 |
| SLOTH 当前实现保存并回读签名 | 算法源码支持 |
| mHBS 相对精简 SLOTH 的具体存储缩减比例 | 待测 |
| 优势不是由额外逻辑、外部缓冲或性能损失换来 | 需要总面积、接口及性能联合评估 |

## 6. 建议实验组织

本节为后续方案，不代表已运行或已取得结果。

### 6.1 对照组

| 组别 | 架构 | 用途 |
|---|---|---|
| A | 原始 SLOTH，保留当前程序和缓冲接口 | 复现现有结果，建立可追溯基线 |
| B | 精简 SHAKE-only SLOTH，移除无关测试/库，按实际参数分配缓冲 | 排除固件冗余和最大数组预留造成的差异 |
| C | 进一步优化为分块或流式输出的软件方案 | 检验优势是否主要来自接口和输出缓冲 |
| D | 当前 mHBS | 测量整体实现效果 |
| 可选机制对照 | RISC-V 驱动与 mHBS 相同的专用数据通路 | 分离微码控制与数据通路特化的收益 |

### 6.2 测量项目

- **控制存储**：`.text`、必要 `.rodata`、微码镜像逻辑容量及物理 ROM 资源。
- **数据容量**：静态数据、算法栈峰值、堆峰值、调用者密钥/消息/签名缓冲；说明哪些同时存活。
- **硬件状态**：CPU 寄存器、Hash 状态、节点数组及其他暂存；报告总 LUT、FF、LUTRAM、BRAM、DSP。
- **流量**：主 RAM 读写字节、签名回读字节、CPU/Hash MMIO 事务、共享存储访问次数。
- **性能**：KG/Sign/Verify 周期、Hash/置换次数、实测可达频率、延迟和 ATP。
- **正确性**：同参数、同消息、同输入随机性下验证输出，并覆盖六种 f/s 参数。

不能直接用“128 KiB÷1,112 LUTRAM”计算缩减比。容量指标以字节或位比较，物理实现以统一器件上的资源比较，两张表分别报告。

### 6.3 mHBS 消融

| 消融项 | 对照设计 | 核心指标 |
|---|---|---|
| 跨阶段存储共享 | FORS 根与 WOTS 端点独立存储 | LUTRAM、逻辑 LUT、周期；已有历史直接对照 |
| 签名流式输出 | 增加完整或分块签名缓冲 | 结果容量、BRAM、输出条件和延迟 |
| 局部反馈 | 中间链值经外部工作存储往返 | 读写流量、周期、FF/LUT 成本 |
| 暂存复用 | 保留独立结果副本 | FF、选择逻辑和时序 |
| 控制表示压缩 | 等价任务展开或处理器控制 | 程序容量、控制面积及执行开销 |

### 6.4 公平性与交付

使用相同支持范围、器件、工具、约束及性能口径。Hash lane 数和轮展开程度优先对齐；无法对齐时分别给出资源和吞吐，而非只比较存储。当前 mHBS 输出无反压，比较双方应使用相同接收条件；若系统需要 FIFO 或整签名外部缓存，应另列容量。

对 SLOTH 栈水位实验保留固件 ELF、编译参数及日志；对硬件保留源码、镜像、综合报告和哈希。分别报告原始、精简和流式软件版本，不能以测试程序的 50 KB 预留缓冲代表所有软件实现。

现有 SLOTH 周期报告不等于内存峰值报告。其“哈希输入构建”列还包含树遍历和其他 CPU 工作，不能用该列周期反推出存储容量或纯数据搬运成本。
