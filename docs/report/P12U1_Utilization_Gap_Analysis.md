# P12U1 相比 P1U1 的 Keccak 利用率为何明显下降

分析日期：2026-10-12。范围：当前单 lane、SLH-DSA-SHAKE-128f Sign、P1U1 与 P12U1；仅分析已有结果，不修改 RTL，不新增 HDL 仿真或综合。

**问题的核心是：model 计算的算法周期下界允许全局利用独立任务，而当前 RTL 只在部分链/叶任务中并行，普通请求独占计算流水，且按整批推进。P 增大后，这些限制浪费的计算容量随之放大。**

但 model 的利用率上界也不是已经实现、或者已经证明可达的调度结果。不能将所有实测差距归结为必然可消除的实现开销。

## 1. 比较对象与口径

来源：

- [13 组实测报告](Single_Lane_13_ATP_150_110.md)、[JSON](Single_Lane_13_ATP_150_110.json)。
- [理论下界报告](Keccak_Theoretical_Bounds.md)、[JSON](Keccak_Theoretical_Bounds.json)、[模型说明](../Keccak_Theoretical_Model.md)。
- [P1U1 仿真记录](../../manifests/experiments/single_lane_13_20261009_v4/P1U1/simulation.json)、[P12U1 仿真记录](../../manifests/experiments/single_lane_13_20261009_v4/P12U1/simulation.json)。

已核对两份分析的种子、公钥根、消息和签名输出一致；相关控制器、recipe lane、链上下文 RTL 及 `model/unified_hbs.py` 的 SHA-256 与 v4 实验配置中的冻结源码一致。不是不同算法、不同消息或不同版本造成的表面差异。

两组均完成 **104,937 次 Hash、105,641 次 Keccak 置换**。每次置换需要 24 轮，因此有效轮工作量为：

```text
W = 105,641 × 24 = 2,535,384 轮
利用率 η = W / (P × U × 计算周期)
空闲率   = 1 − η
```

这里的“空闲”是**有效轮计算容量没有被使用**，不是电路停止翻转，也不是时钟门控率。它包含整条流水空闲和只有部分级在做有效计算两种情况。

| 指标 | P1U1 | P12U1 |
|---|---:|---:|
| 组合 Keccak 轮实例数 P×U | 1 | 12 |
| 实测计算周期 | 2,619,719 | 342,457 |
| model 周期下界 | 2,535,384 | 211,296 |
| 实测有效轮利用率 | 96.7808% | 61.6959% |
| 实测容量空闲率 | 3.2192% | 38.3041% |
| model 利用率上界 | 100% | 99.9934% |
| model 空闲率下界 | 0% | 0.0066% |

实际计算容量增加 12 倍，签名却只加速了 **7.6498 倍**。因此：

```text
η(P12) / η(P1) = T(P1) / (12 × T(P12)) ≈ 0.6375
```

利用率下降约 **35.08 个百分点**，并不意味着 P12 更慢；P12U1 仍是原报告中周期最少、ATP 最低的配置。

## 2. model 为什么几乎没有下降

### 2.1 model 的并行范围大于当前 RTL

model 采用理想同时批次：每批最多 P 个独立置换同时开始，经过 `24/U` 周期同时结束。它不限制逐个发射、存储端口、结果暂存容量，也不加入状态机和输出周期。

算法输入就绪后，model 中的独立任务可以跨树、跨链并行：

- FORS 不要求完成树 0 后才能开始树 1；各树的叶和就绪父节点可以交错。
- 父节点只依赖自己的两个子节点，不依赖其他树或其他无关叶子。
- 普通父节点与独立叶/链任务没有全局互斥边。
- WOTS 完整端点链可在所需地址就绪后计算；仅为选取签名 capture 所需的消息数据，不会让所有完整端点链都等待。
- 多块 Hash 保留块间依赖，但不禁止其他独立任务填补剩余批次位置。

**这里的“可以”指依赖图不禁止，并非已经生成了对应硬件执行时序。**

### 2.2 当前数学下界主要由总工作量决定

本用例图中的最长置换依赖链为 **41 个节点**。对于 P12，总工作量约束给出：

```text
至少需要的批次数 = ceil(105,641 / 12) = 8,804
每批周期         = 24
周期下界         = 8,804 × 24 = 211,296
```

模型的正向深度、反向深度及联合依赖窗口检查没有得到比 8,804 批更大的下界。因此最终值基本就是容量下界：

```text
8,804 × 12 = 105,648 个置换位置
位置数 − 任务数 = 7
空闲率下界 = 7 / 105,648 ≈ 0.0066%
```

这不是证明“算法只能产生 7 个空位”，而是说：**目前这些必要条件只能证明至少有 7 个空位，还没有证明更多空位不可避免。**

尤其不能用“最长链只有 41”推出没有串行损失；它必须与其他依赖及资源约束一起判断。当前分析没有求解完整最优调度，未证明 8,804 批可达。

## 3. RTL 实际只让部分任务并行

### 3.1 批量链/叶路径

[控制器](../../rtl/top/mhbs_hbs.sv)的 `CHAIN_SETUP` 只在符合 SLH 配方且 P>1 时进入批量路径。主要覆盖：

- 同一个 WOTS 叶的多条独立链；
- 同一棵 FORS 树的一批连续叶任务。

基本过程为：

```text
准备本批任务
  → PIPE_ISSUE：逐拍发射，遇到 ready=0 则等待
  → PIPE_WAIT：等全部预期槽位完成
  → 消费结果 / capture，必要时输出或合并父节点
  → 准备下一批
```

WOTS 端点可完成即写回，但“结果已写回”不代表“控制器立即给该槽补新任务”。`advance_direct_batch` 明确在整批完成及必要 capture 消费后才推进下一批。

FORS 则将计算完成的叶节点按叶索引顺序加载和消费，使用现有树栈合并父节点。在这个阶段不持续发射其他树的独立工作。

### 3.2 普通路径与批量路径互斥

[recipe lane](../../rtl/hash_lane/mhbs_recipe_lane.sv)使用：

```systemverilog
issue_valid = batch_mode ? batch_perm_valid : normal_valid;
normal_valid = hash_state == HASH_RUN && !sent;
```

普通请求只有一份在途 sponge 请求；其内部置换/跨块处理仍按依赖推进。消息处理、端点列表压缩、父节点合并走这条路径。

这意味着：

```text
model：    普通父节点 + 其他独立叶/链，可共享理想批次容量
当前 RTL：批量任务结束 → 普通请求独占流水 → 再回到批量任务
```

每次普通请求的结果确实需要等待；**是否禁止同时执行其他无关任务，则是当前架构的选择，不是该父子依赖本身的要求。**

## 4. 量化普通请求独占流水的影响

使用现有 `Machine` 的逐配方观察器，按本次同一输入重新统计工作量，得到以下结果。这里重算的是软件配方计数，不是新做 RTL 阶段周期测量。

| 配方 | Hash 次数 | 置换次数 | P12 当前路径 |
|---|---:|---:|---|
| 消息随机值 | 1 | 1 | 普通 |
| Hmsg | 1 | 1 | 普通 |
| FORS 秘密值生成 | 2,112 | 2,112 | 批量叶任务 |
| FORS 叶哈希 | 2,112 | 2,112 | 批量叶任务 |
| FORS 父节点 | 2,079 | 2,079 | 普通 |
| WOTS 链种子 | 6,160 | 6,160 | 批量链任务 |
| WOTS 链步骤 | 92,145 | 92,145 | 批量链任务 |
| WOTS 端点列表压缩 | 175 | 875 | 普通 |
| Hypertree 父节点 | 151 | 151 | 普通 |
| FORS 根列表压缩 | 1 | 5 | 普通 |
| **合计** | **104,937** | **105,641** | |

普通路径共 **3,112 次置换**，占全部置换的 **2.9458%**；批量路径为 **102,529 次**。

### 4.1 为什么 2.95% 的工作量会造成约 20 个百分点闲置

P1U1 执行一个普通置换时，唯一组合轮可以连续工作24周期，Keccak 计算部分没有因并行度产生的容量空闲。

P12U1 执行一个孤立普通置换时，该状态要穿过12级两遍，总共仍需至少24周期。期间只有一个有效上下文在移动：按有效轮计算，平均只占用12份计算容量中的一份。流水级不是固定分给某棵树，而是处理流经的状态。

对这 3,112 次普通置换：

```text
最低计算时间              = 3,112 × 24 = 74,688 周期
有效轮工作量              = 74,688 轮
期间可提供的轮容量        = 74,688 × 12 = 896,256 轮位置
因单上下文产生的空轮位置  = 74,688 × 11 = 821,568
```

整个 P12U1 签名提供的容量是：

```text
342,457 × 12 = 4,109,484 轮位置
821,568 / 4,109,484 ≈ 19.9920%
```

因此，**普通请求独占流水这一结构限制，至少对应当前完整执行约20个百分点的容量闲置**。普通请求前后的状态跳转、吸收及握手空拍尚未计入这部分。

“20个百分点”不是说有20%的时钟完全不工作；上述计算期间，流水仍有一部分有效轮在工作。它也不是逐拍观察器实测的阶段归因。

### 4.2 保持这条限制，即使其他部分完美并行也到不了100%

如果批量部分可以完全占满12份容量，普通部分仍逐个置换执行，则周期仍至少为：

```text
T_arch_lb = 普通置换数 × 24 + 批量置换数 × 24 / 12
          = 3,112 × 24 + 102,529 × 24 / 12
          = 279,746 周期

η_arch_upper = 2,535,384 / (12 × 279,746)
             ≈ 75.5264%
```

这是针对当前“普通与批量互斥、普通单上下文”限制推导的**架构上界**；它仍忽略批次边界、发射、存储、输出和控制成本，也未证明可达。

| 比较层次 | 周期下界／实测周期 | 利用率上界／实测利用率 |
|---|---:|---:|
| model 算法下界：理想同时批次，可跨任务类别并行 | 211,296 | 99.9934% |
| 加入普通请求独占限制：其余容量完美利用的下界 | 279,746 | 75.5264% |
| 当前 RTL 实测 | 342,457 | 61.6959% |

第二行只使用轮容量约束，没有再强制所有任务按24周期的整批对齐，所以它与第一行的整数批次取整口径略有区别；两者都是下界，不应当成可执行时序。

## 5. 其余空闲来自哪里，能确定多少

根据总周期和工作量，可以精确计算总容量缺口：

```text
总空轮位置 = 12 × 342,457 − 2,535,384 = 1,574,100
```

扣除上述普通请求计算窗口内必然空出的容量：

```text
其余空轮位置 = 1,574,100 − 821,568 = 752,532
             = 全部容量的 18.3121%
             = 62,711 个“12轮容量全空”的等效周期
```

因此已有证据支持以下容量账目：

| 项目 | 占完整 P12U1 容量 |
|---|---:|
| 有效轮工作量 | 61.6959% |
| 普通置换计算窗口中的单上下文空位 | 至少19.9920% |
| 扣除上述最低单上下文损失后的其余容量缺口 | 18.3121% |
| 合计 | 100% |

这里按普通置换的最低24周期计算窗口划分，额外的普通路径开销归入最后一项。62,711是容量等效周期，不能理解为已测得一段连续的全空闲时间。

代码中可确认其余损失的来源包括：

1. **整批屏障**：已经完成的槽位不立即补任务；短链先完成时仍需等待长链及批次消费。普通 WOTS 全长链通常等长，不能把所有批次都说成严重长短不均。
2. **发射和排空**：实际只有一个置换输入端口，任务逐拍接受，且循环反馈和链反馈优先；model 允许P个任务同时开始。长链连续反馈期间可以保持较高吞吐，不能将每次反馈都算作新一轮空泡。
3. **FORS 消费与父节点处理**：叶批次完成后按序加载、入栈、合并，不趁此发射其他树或下批任务。父节点的有效24轮和单上下文空位已计入第4节，不能重复归因；这里额外指数据搬运、控制和批次切换。
4. **尾批**：WOTS 每叶35条链，P12通常分成12+12+11；FORS 每树64个叶，分成5批12个及最后4个。只在最后一批不满，不能按最差尾批占用率代表整棵树。此例全部WOTS槽位数量比例为35/36，FORS为64/72；这只是槽位数量示意，并非完整执行的实测占用率。
5. **输出及普通 sponge 辅助状态**：capture/认证路径输出、流式吸收、填充准备、状态跳转和请求响应处理；外部无额外等待也不代表核内这些动作零周期。

**目前没有逐拍阶段统计，不能把剩余18.3121%精确拆成以上五项各占多少。** 尤其不能直接断言其中最大项是尾批、发射或输出。

## 6. 为什么 P1 的影响小，而 P12 被放大

P1 没有“同一周期还剩11份计算容量”的问题。普通 Hash、父节点、多块 Hash 只要持续计算，就能使用唯一的组合轮。

P12 的峰值容量增大12倍，但下列时间没有同比缩短：

- 单上下文普通置换依然需24轮；
- 状态机、结果消费和输出动作仍需执行；
- 整批完成后才能切换下一批的规则仍存在。

P1 的容量缺口为 **84,335轮位置／周期**，P12 为 **1,574,100轮位置**。两者不能直接作为墙钟开销相减：P12 每周期提供12个轮位置。

也不能把 P1 的84,335周期全部当作P12固定开销再加到理想周期上，因为 P1 与 P>1 使用不同的链执行路径，部分控制操作被批处理摊薄，另一些引入新的发射和批次开销。

## 7. 对“算法本来就考虑空泡”的准确回答

这个前提需要分开理解：

- **是的，model 已记录父子节点、链步骤及多块 Hash 的依赖。** 它没有把所有置换直接当成独立任务。
- **但它没有加入当前 RTL 的普通/批量互斥、单树推进、整批消费和有限结果暂存限制。** 这些额外限制使实际可调度的任务范围更窄。
- **而且 model 输出的是必要条件导出的下界。** 没有构造达到上界的调度，算法实际最优空闲率可能高于0.0066%。

所以，不能说“P12有38.3%空闲是算法已经允许的，正常接受即可”；也不能说“理论只空0.0066%，38.3%就都能消掉”。

已有数据能确认：**普通请求独占流水造成了很大的、超出当前算法模型的架构限制；批次及控制机制继续扩大差距。剩余可优化空间，需要在具体调度与存储约束下测量。**

## 8. 若后续优化，应验证什么

本报告不实施优化。依据现有证据，值得优先验证的是：

- 让父节点/短普通请求与其他树的独立叶任务共用多上下文调度，打破任务类别互斥；仅改善 WOTS 下一批发射无法消除上述普通路径限制。
- 跨 FORS 树保留必要的进度和节点，持续发射就绪任务；不是给每个流水级固定分配一棵树。
- 在结果、capture及认证路径生命周期正确的前提下补任务，并评估新增存储、仲裁对面积和频率的影响。
- 增加按普通/批量路径及各级有效位统计的纯仿真观察器，进一步拆解剩余空闲；所有阶段采用互斥分类，避免重复计数。
- 若要把model上界当成具体优化目标，先构造一个可执行的依赖图调度，再逐步加入实际上下文和存储限制。

提高利用率是手段，最终仍应以输出正确、完整操作周期和面积/频率对应的ATP评价；当前P12U1已经比P1U1快7.65倍，不能仅因利用率较低而判断设计收益为负。
